# Terraform provider for Plerion

The Plerion provider manages [Plerion](https://www.plerion.com) resources through the Plerion customer API. It covers custom checks: create, update, import and delete rego checks, look them up, and preview their findings with a dry run before applying a change.

User documentation lives in [`docs/`](docs/) and is published to the Terraform Registry. Start with [`docs/index.md`](docs/index.md).

## Using the provider

```terraform
terraform {
  required_providers {
    plerion = {
      source  = "plerionhq/plerion"
      version = "~> 0.1"
    }
  }
}

provider "plerion" {
  # Or set PLERION_API_URL and PLERION_API_KEY.
  api_url = "https://us1.api.plerion.com"
}

resource "plerion_custom_check" "github_oidc_roles" {
  slug  = "github-oidc-roles-must-pin-a-repository"
  title = "GitHub OIDC roles must pin a repository"

  target = {
    asset_type = "AWS::IAM::Role"
    scope      = "batch"
  }

  defaults = {
    severity_level = "HIGH"
    message        = "The role trusts GitHub OIDC without limiting which repository can assume it."
  }

  body = file("${path.module}/policies/github-oidc-roles.rego")
}
```

## Requirements

- Go 1.26 or later, to build the provider.
- Terraform 1.5 or later, or OpenTofu, to use it. The tests use the `terraform` binary on your `PATH`; set `TF_ACC_TERRAFORM_PATH` to test with another binary.
- Terragrunt 1.1 or later, `jq` and `curl`, for the end-to-end tests only.

## Developing

Build and run the unit tests:

```sh
make build
make test
make lint
```

To try a local build in your own Terraform configuration, install it and point Terraform at it with a development override. Terraform then skips the registry for this provider:

```sh
make install
```

```hcl
# ~/.terraformrc
provider_installation {
  dev_overrides {
    "plerionhq/plerion" = "/Users/<you>/go/bin"
  }
  direct {}
}
```

### Repository layout

| Path | Contents |
| --- | --- |
| `internal/client` | The HTTP client for the Plerion customer API: authentication, retries and error parsing. |
| `internal/provider` | The provider, the `plerion_custom_check` resource and the data sources. |
| `internal/fakeapi` | An in-memory copy of the custom checks API that the provider tests run against. |
| `examples/`, `templates/` | The examples and page templates the documentation is generated from. |
| `docs/` | Generated documentation. Do not edit it by hand. |
| `tests/terragrunt` | The end-to-end suite that runs against a real Plerion API. |

## Tests

There are two suites.

**Unit and provider tests** run with `make test` and need no credentials. The provider tests drive the real Terraform CLI against `internal/fakeapi`, which copies the API behavior the provider depends on: full replacement on update, unique slugs, and metadata returned with its keys in a different order. When the real API changes, change the fake API in the same pull request.

**End-to-end tests** run the provider against a real Plerion API through Terragrunt. They create checks, check that a second plan shows no changes, update them, repair changes made outside Terraform, import by slug, test a slug conflict and destroy everything. See [`tests/terragrunt/README.md`](tests/terragrunt/README.md).

```sh
PLERION_API_URL=https://<api-address-of-your-test-tenant> \
PLERION_API_KEY_FILE=~/path/to/key \
make e2e
```

## Documentation

The pages in `docs/` are generated by [tfplugindocs](https://github.com/hashicorp/terraform-plugin-docs) from three sources:

- the `MarkdownDescription` of each schema attribute in `internal/provider`,
- the page templates in `templates/`,
- the examples in `examples/`.

Change one of those, then run `make docs` and commit the result. `make lint` fails when `docs/` is out of date.

Product-facing text, which covers schema descriptions, error messages, templates and examples, uses American English and plain sentences, with no em dashes.

## Changelog

Add an entry to [`CHANGELOG.md`](CHANGELOG.md) under the unreleased version in the same pull request as the change. Entries are written for customers: say what changed for them, not how the code changed.

## Releasing

Releases are built by GoReleaser from a version tag and signed with the Plerion GPG key, which the Terraform Registry requires.

1. Move the unreleased changelog entries under the new version number and today's date.
2. Tag the commit on `main`, for example `git tag v0.2.0`, and push the tag.
3. Approve the waiting `release` deployment in the workflow run. The signing key lives in the `release` environment, which only version tags can use and which needs an approval before the job starts.
4. The workflow builds the binaries, signs the checksums and creates a GitHub release. The Terraform Registry picks up the release from there.

The private signing key and its passphrase are the `GPG_PRIVATE_KEY` and `PASSPHRASE` secrets of the `release` environment. A copy of both is kept in 1Password.
